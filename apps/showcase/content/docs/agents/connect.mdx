A calendar is reachable by agents once your app creates ui-sdk's agent bridge. The bridge lists the
calendar, runs an agent's steps on it, and asks your `allow` before each one. This page sets that
up. <React>Its samples import the `Calendar`, `Meeting`, `meetings` and `weekRules` that the
[Quick start](/docs/quick-start) puts in `calendar.tsx`.</React><Solid>Its samples import the

The bridge comes from <React>`@ui-sdk/react/agent`. `@ui-sdk/react`</React><Solid>`@ui-sdk/solid/agent`. `@ui-sdk/solid`</Solid> is one of the calendar's peer
dependencies, so [Installation](/docs/installation) already added it. Create one bridge for the
whole app, in a module of its own:

The bridge finds the calendars already on the page and hears new ones as they mount. It covers
every ui-sdk component in your app, not only calendars. On the server it lists nothing, so the
module is safe to import from a component that renders there.

Creating the bridge connects nothing to a model. It gives your code four methods:

| Method                      | What it does                                                                          |
| --------------------------- | ------------------------------------------------------------------------------------- |
| `agent.snapshot()`          | Lists every component on the page                                                     |
| `agent.query({ within })`   | Finds components, or the events one calendar shows. Resolves with the list            |
| `agent.act({ steps })`      | Runs steps in order. Resolves with what each one did                                  |
| `agent.subscribe(listener)` | Calls `listener` when a component's state changes. Returns the function that stops it |

You hand those to an agent in one of two ways: [WebMCP](/docs/agents/webmcp) for the agent built
into a browser, or [your own server](/docs/agents/server) for a model you run.

Without `label`, the calendar is named by its title, such as "Oct 5 – 11, 2026", and the title
changes each time the agent navigates. With two calendars on a page, give each its own `label`.

The bridge finds a calendar by its `Calendar.Frame`. A `Root` that renders its views without a
frame works for a person and isn't listed for an agent.

`applyChange`, `titleFrom` and `timedOnly` are this example's own. `applyChange` is what saving
means here, and `timedOnly` is a [policy](/docs/interactions#policies) that refuses an all-day
meeting:

Without `onEventChange` the calendar is read-only for agents as well. An agent can still read it
and navigate. The actions that change an event leave its `actions`, and `describeCalendar` reports
`readOnly: true`.

## Save what the agent sent

The calendar knows when an event is and which resources it's on. Everything else about an event is
your record's, so the calendar can't write it. An agent sends those values, and your handler
stores them.

An agent's `createEvent` and `updateEvent` take two inputs for that: `title`, and `fields`, an
object of whatever your events have.

```json
{
  "ref": "Team calendar",
  "action": "createEvent",
  "args": [
    {
      "start": "2026-10-06T14:00",
      "end": "2026-10-06T15:00",
      "title": "Customer call",
      "fields": { "color": "green" }
    }
  ]
}
```

Your `onEventChange` gets them as `detail.fields`, with the title folded in:

```ts
// change.cause === "create", change.event === null, detail.input === "agent"
detail.fields; // { color: "green", title: "Customer call" }
```

What each change brings:

| Step          | `change.cause`               | `change.proposed`                      | `detail.fields`                    |
| ------------- | ---------------------------- | -------------------------------------- | ---------------------------------- |
| `createEvent` | `"create"`                   | The new event's times and resources    | `title` and `fields`, when sent    |
| `updateEvent` | `"update"`                   | The event's times, new or as they were | `title` and `fields`, when sent    |
| `moveEvent`   | `"move"`                     | The new times                          | Absent: the action takes no fields |
| `resizeEvent` | `"resize-start"` or `"-end"` | The new times                          | Absent                             |
| `deleteEvent` | `"delete"`                   | `null`                                 | Absent                             |

Three rules for the handler, which `applyChange` above follows:

- **Check every field.** The calendar passes `fields` on as the agent sent them. It checks that
  `fields` is an object and `title` a string, and nothing inside: a value can be any type, nested
  to any depth. `titleFrom` takes a title only when it's a non-empty string; treat each field of
  yours the same way, as you would a form's input.
- **An update can bring fields alone.** `updateEvent` with only a `title` proposes the event's
  current times, so keep storing `change.proposed` and read the title beside it.
- **A person's change has no fields.** A drag, a resize and an undo arrive without
  `detail.fields`, so fall back to what the event had.

A policy gets the same detail as its second argument's `detail`, so a rule can read a field before
anything is saved: refuse an agent's create without a title, or a title that's too long. The agent
reads the policy's reason in the failed step.

What the handler doesn't store is dropped without a word to the agent. If your app takes only some
fields from an agent, say which in the model's prompt, or refuse the others in a policy.

An action takes one object, never a list of values. `args: ["review", "2026-10-09T10:00"]` fails,
and the message says what the action takes:

```text
calendar-agent-invalid-arguments: moveEvent takes { eventId: ID, start: ISO date or date-time, end?: same, resourceIds?: ID[] }; it takes one object, not 2 arguments
```

`ref` takes the calendar's label, its ref from the snapshot, or its kind, `"calendar"`. A name that
fits two components fails the step and lists both, so use the ref then. <React>The registry's toolbar
adds its buttons and its view select to the snapshot, ahead of the calendar, so the calendar's ref
depends on what else is on the page.</React><Solid>The calendar's ref depends on which other ui-sdk
components are on the page.</Solid> Its label doesn't.

In the object `snapshot()` returns, `anchorDate` is a `Temporal.PlainDate`. It becomes the string
`"2026-10-08"` when the snapshot is sent as JSON, which is how a model gets it.

Without `allow`, a bridge runs every step. Pass `allow` to `createAgent` to decide step by step.

`allow` gets the step after the bridge found its component:

| Field       | Contents                                                                      |
| ----------- | ----------------------------------------------------------------------------- |
| `component` | The component's kind: `"calendar"` for a calendar                             |
| `label`     | The component's label, such as `"Team calendar"`                              |
| `ref`       | The component's ref, such as `"c1"`                                           |
| `action`    | The action, such as `"moveEvent"`                                             |
| `args`      | The input as the agent sent it, such as `[{ eventId: "review", start: "…" }]` |
| `confirm`   | The text of a `data-agent-confirm` mark on the component, if it has one       |

Return `true` to run the step and `false` to refuse it. A refused step fails with a message the
agent reads, and the steps after it don't run:

```json
{
  "ok": false,
  "error": { "step": 1, "message": "The app refused moveEvent on c7." },
  "steps": [{ "step": 0, "ref": "c7" }],
  "appeared": [],
  "values": {}
}
```

Start from a list of what's allowed, as the example does, so an action added in a later version
stays refused until you choose it. `allow` can also return a promise, which is how you
[ask the person first](/docs/agents/deleting).

Put the reading actions on that list. `describeCalendar`, `listEvents` and `getChange` are steps
like any other, and `allow` is asked for them. An agent that may move events and may not list them
has no event IDs to move. `allow` sees `args` before the calendar checks them, so read them as
unknown input.

A step isn't always one of the calendar's actions. An agent can also press a ui-sdk button of
yours, as a step with the action `press`, and what its handler does to the calendar counts as the
agent's: your policies and `onEventChange` hear `input: "agent"`. The example's `allow` refuses
every component but the calendar, so no button is pressed there. If yours lets presses through,
decide them as carefully as the calendar's own actions, a
[delete button](/docs/agents/deleting#a-delete-button-of-yours) most of all.

`allow` covers steps. The bridge's own `snapshot` and `query` aren't steps: they answer whatever
`allow` says, with the calendar's entry and the events in view. To keep a calendar from agents
entirely, put `data-agent-hidden` on an element around it:

<React>

<include meta='title="agent-hidden.tsx"'>../../examples/agent-hidden.tsx</include>

</React>

<Solid>

<include meta='title="agent-hidden.tsx"'>../../examples/solid/agent-hidden.tsx#hidden</include>

</Solid>

That calendar is left out of `snapshot` and `query`, and a step that names it fails with
`"Private calendar" isn't available to agents here. Ask the person.`

`allow` is the first of three checks an agent's change passes. The second is your
[policies](/docs/agents/changes#refuse-an-agents-change), which see the change itself: the event,
where it would land, and who proposed it. The third is your `onEventChange`, which can refuse to
save.

## If the agent sees nothing

When `agent.snapshot()` returns `[]` while a calendar is on the page, a step fails with a message
that starts `No component "Team calendar" on the page.` The usual cause is that the bridge and the
calendar run on two copies of `@ui-sdk/core`. Each copy keeps its own list of components, so the
bridge's copy never hears of the calendar.

Check these first:

- **A frame.** The calendar renders `Calendar.Frame` inside `Root`. Without one it isn't listed.
- **One version.** `@ui-sdk/core` and <React>`@ui-sdk/react`</React><Solid>`@ui-sdk/solid`</Solid> are installed once, at the same version.
  `pnpm why @ui-sdk/core` or `npm ls @ui-sdk/core` shows more than one when they aren't.
- **One import path for the bridge.** Import `createAgent` from
  <React>`@ui-sdk/react/agent`</React>
  <Solid>`@ui-sdk/solid/agent`</Solid>, the adapter your calendar uses.
  <React> A Solid app imports it from `@ui-sdk/solid/agent`.</React>
- **The dev server's pre-bundle.** Vite pre-bundles dependencies in development. When one package
  that imports `@ui-sdk/core` is kept out of the pre-bundle and another isn't, the page loads the
  core twice. Solid's Vite plugin does that for `@ui-sdk/solid`. Keep the core out as well:

```ts title="vite.config.ts"
import { defineConfig } from "vite";

export default defineConfig({
  optimizeDeps: {
    // One copy of the core, unbundled, for the calendar and the bridge alike.
    exclude: ["@ui-sdk/core"],
  },
});
```

With two copies the calendar's own parts can stop following its state too, so a toolbar that no
longer updates is the same problem. Check a new setup in the browser: mount a calendar, call
`agent.snapshot()`, and expect one entry with `component: "calendar"`.
