Moltenship Time handles the hard parts of a calendar: dates, time zones, navigation, calendar
state, fast event lookups, and saving changes. Your events stay in the shape your app already uses,
and Time reads them through a small adapter. The week, day, month, year, agenda and resource views are
source files you copy into your app, so you can change how they look and behave. An AI agent can
read the same calendar and act on it through named actions, under rules your app sets.

## Who it's for

Time is for developers building scheduling screens (bookings, rooms, shifts, team calendars) who
want to:

- keep their existing event data and API,
- style the calendar with their own design system, or start from shadcn/ui,
- get time zones and daylight saving time right without writing that math themselves,
- let an AI agent work with the calendar without handing it the page's markup.

The calendar and its views are for React 19. A [SolidJS 2 package](/docs/api/solid) renders the
same calendar without the views, as a preview.

[Comparison](/docs/comparison) sets Time beside FullCalendar and react-big-calendar, including
where they're ahead.

## What you get today

- **Built-in views.** [Week, day](/docs/views/week-and-day), [month](/docs/views/month),
  [year](/docs/views/year), [agenda](/docs/views/agenda),
  [resource columns](/docs/views/resource-columns) and
  [resource timeline](/docs/views/resource-timeline), plus week, day, month and agenda views that
  [scroll without end](/docs/views/scrolling), in the style of Google Calendar, built on shadcn/ui and Tailwind
  CSS. A [theme](/docs/theming) with calendar tokens and an event color palette comes with them.
- **Your data, read through an adapter.** You describe how to read an ID, title, and time range
  from your records. TypeScript keeps your record and ID types all the way through.
- **Three kinds of time.** Timed events use `Temporal.Instant`, all-day events use
  `Temporal.PlainDate`, and floating events use `Temporal.PlainDateTime`. No `Date` objects.
- **Time zone and DST handling.** Days that are 23 or 25 hours long and skipped or repeated hours
  are handled for you.
- **Editing.** Moves, resizes, creates, and deletes arrive as changes for you to save. They show
  as pending while they save, roll back if saving fails, and pass through policies you choose. See
  [Interactions](/docs/interactions). The built-in views support dragging, resizing, and creating
  events with the mouse, a pen, or touch.
- **Controlled or uncontrolled state.** The visible date, view, time zone, selection, and focus can
  each be owned by the calendar or by your app.
- **Headless parts.** `Root`, previous/next/today buttons, `Title`, and `ActiveView` render plain
  elements, and [custom views](/docs/views/custom-views) are a strategy plus a component.
- **Ready for agents.** A calendar gives an AI agent fifteen actions: describe the calendar, list
  its events, navigate, switch view, and create, rename, move, resize and delete events. An
  agent's change goes through your policies and your `onEventChange`, marked as an agent's, and
  the agent gets back how it ended. Deleting is off until you turn it on. It works with the agent
  built into a browser through WebMCP, or with a model you run. See [Agents](/docs/agents).
- **Docs your coding agent can read.** Every page has a Markdown version, the docs ship inside
  the npm package, and a skill teaches a coding agent the library. See
  [Build with a coding agent](/docs/agents/coding-agents).
- **Server rendering.** During server rendering, Time doesn't read the clock, the host time zone, or
  `window`, so the server and the browser render the same markup from the same props.
