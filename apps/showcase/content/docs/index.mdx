Moltenship Time is a calendar for scheduling screens such as bookings, rooms, shifts and team
calendars. Its engine handles dates, time zones, recurrence, calendar state, event lookups and
saving changes, and it imports no UI framework. React renders it. A SolidJS 2 package, a preview,
renders the parts and leaves the views to you. Your events stay in the shape your app already uses, and Time reads them through an
adapter. The week, day, month, year, agenda and resource views are React source files you copy into
your app. An AI agent can read the same calendar and act on it through named actions, under rules
your app sets.

<CalendarPreview switcher />

To see every view with more data, try the [live demo](https://moltenship-time-demo.vercel.app), a
Google Calendar-style app built from the same views. A switch in it opens the
[Solid demo](https://moltenship-time-demo.vercel.app/solid/), which has a month grid and an agenda
you can drag events in, undo and redo, and an agent panel.

## Who it's for

Time is for developers who build scheduling screens and want to:

- keep their existing event data and API,
- style the calendar with their own design system, or start from shadcn/ui,
- get time zones and daylight saving time right without writing that math themselves,
- let an AI agent work with the calendar without handing it the page's markup.

[Comparison](/docs/comparison) sets Time beside FullCalendar and react-big-calendar, including
where they're ahead.

## What you get today

The engine, the calendar's state, the keyboard, the gestures and the hooks are the same in React
and Solid. The ready-made views and the testing package exist in React only.
[React and Solid](/docs/frameworks) has the full table.

### In React and in Solid

- **Your data, read through an adapter.** You describe how to read an ID, a title and a time range
  from your records. TypeScript keeps your record and ID types in every hook and callback.
- **Three kinds of time.** Timed events use `Temporal.Instant`, all-day events use
  `Temporal.PlainDate`, and floating events use `Temporal.PlainDateTime`. No `Date` objects.
- **Time zones and daylight saving time.** The engine lays out days that are 23 or 25 hours long,
  and hours that a clock change skips or repeats. See [Time and time zones](/docs/concepts/time).
- **Recurrence and iCalendar.** `@moltenship/calendar-recurrence` expands RRULE series inside the
  dates on screen, and `@moltenship/ics` parses ICS feeds. Neither imports a framework.
- **Changes you save.** A move, a resize, a create or a delete arrives as a change in
  `onEventChange`. It shows as pending while it saves, rolls back if saving fails, and passes
  through policies you choose. See [Interactions](/docs/interactions).
- **Controlled or uncontrolled state.** The calendar or your app can own the visible date, the
  view, the time zone, the selection and the focus, one value at a time.
- **Headless parts.** `Root`, the previous, next and today buttons, `Title` and `ActiveView` render
  plain elements. A [custom view](/docs/views/custom-views) is a strategy and a component. The
  registry's React views are one UI built on these parts, and
  [Customization](/docs/customization) shows how to restyle it, edit it or build your own.
- **Actions for agents.** A calendar gives an AI agent fourteen actions, and a fifteenth, deleting,
  when you allow it. They describe the calendar, list its events, navigate, switch view, and
  create, rename, move and resize events. An agent sees nothing until your app creates ui-sdk's
  agent bridge. An agent's change goes through your
  policies and your `onEventChange`, marked as an agent's, and the agent gets back how it ended.
  A browser's built-in agent reaches them through WebMCP, an experimental browser API, and a model
  you run reaches them through `agentTools`. See [Agents in your app](/docs/agents).
- **Editing by pointer and keyboard.** `useCalendarPointer` turns drags into moves, resizes and
  creates, with a mouse, a pen or touch, and `useCalendarKeyboard` moves focus through a view and
  moves and resizes events [from the keyboard](/docs/accessibility#changing-events). The
  `Announcer` says each step to a screen reader.
- **Undo and redo.** `createEventHistory` records changes, and `useCalendarHistory` and its
  keyboard shortcuts take them back. See [Undo and redo](/docs/undo-redo).
- **Server rendering.** During server rendering, Time doesn't read the clock, the host time zone or
  `window`, so the server and the browser render the same markup from the same props.
- **Docs your coding agent can read.** Every page has a Markdown version, the docs ship inside
  `@moltenship/calendar@next`, and a skill teaches a coding agent the library. See
  [Build with a coding agent](/docs/agents/coding-agents).

### In React

- **Built-in views.** [Week, day](/docs/views/week-and-day), [month](/docs/views/month),
  [year](/docs/views/year), [agenda](/docs/views/agenda),
  [resource columns](/docs/views/resource-columns) and
  [resource timeline](/docs/views/resource-timeline), plus week, day, month and agenda views that
  [scroll without end](/docs/views/scrolling). They are source files built on shadcn/ui and
  Tailwind CSS, or on [StyleX](/docs/stylex), with a [theme](/docs/theming) of calendar tokens and
  an event color palette.
- **Editing in the built-in views.** The views bind the pointer and the keyboard, and the
  registry's undo toast offers to take each change back.
- **A testing package.** [`@moltenship/calendar-testing`](/docs/testing) has a fixed clock, typed
  builders, a render harness, and keyboard and pointer drivers.

### In Solid, as a preview

`@moltenship/calendar-solid` has the parts and hooks React has, so a view you write gets keyboard
navigation, dragging, drafts and undo. It has no ready-made views and no testing package yet. See
[Solid](/docs/api/solid).
