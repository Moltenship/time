`@moltenship/calendar-solid` is the calendar for [SolidJS](https://www.solidjs.com) 2. It renders
the same [primitive](/docs/api/primitives) as the React integration, so both share one
implementation of the calendar's state, actions and event changes, [agent actions](/docs/agents)
included.

<Callout type="warn" title="A preview">
  This package is new in 2.0 and its API can change in any release before 2.0.0. It has every part
  and hook React's integration has, keyboard navigation, dragging, drafts and undo included, and the
  actions an agent can call. It has no ready-made views and no testing package yet: see [what isn't
  in it yet](#what-isnt-in-it-yet). The rest of these docs describe React.
</Callout>

Time 2.0 is a pre-release on npm's `next` tag, so the command installs `@next`.

- **`@moltenship/calendar-core`** has the event adapter and the functions a view is made of. The
  Solid package doesn't re-export them.
- **`solid-js` and `@solidjs/web`** 2.0, and **`@ui-sdk/core` and `@ui-sdk/solid`** from
  `0.1.0-beta.16` on within the 0.1 line, are peer dependencies.
- **Don't install `@moltenship/calendar`.** It's the React package, and it doesn't re-export this
  one.
- A runtime with `Temporal`, or a polyfill that defines `globalThis.Temporal`, loaded before the
  calendar, and TypeScript 6 or later with `"lib": ["DOM", "DOM.Iterable", "ESNext"]`. Both are the
  same as for React: see [Installation](/docs/installation).

### Build setup

The integration is plain TypeScript, and `@ui-sdk/solid` ships JSX for your app's Solid compiler.
With Vite, use Solid's plugin:

```ts title="vite.config.ts"
import solid from "@solidjs/vite-plugin";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [solid()],
  optimizeDeps: {
    // One copy of ui-sdk's core in the dev server. The calendar and the agent bridge find each
    // other through it.
    exclude: ["@ui-sdk/core"],
  },
});
```

```json title="tsconfig.json"
{
  "compilerOptions": {
    "jsx": "preserve",
    "jsxImportSource": "@solidjs/web",
    "lib": ["ESNext", "DOM", "DOM.Iterable"]
  }
}
```

If the page fails with `React is not defined` from a file in `@ui-sdk/solid`, the plugin didn't
compile that package as Solid. Check that `@ui-sdk/solid` is in your app's own `dependencies`,
where the install command puts it.

## A calendar

There are no ready-made Solid views. A view is a strategy from `@moltenship/calendar-core` and a
Solid component that draws its projection. This one is the engine's list projection as an agenda:

```tsx title="calendar.tsx"
import {
  defineEventAdapter,
  getListRange,
  getListTitle,
  navigateList,
  projectList,
  type CalendarEventInterval,
  type ListProjection,
  type ListViewOptions,
} from "@moltenship/calendar-core";
import {
  createCalendar,
  defineCalendarView,
  type CalendarViewRendererProps,
} from "@moltenship/calendar-solid";
import { For } from "solid-js";

export interface Meeting {
  readonly id: string;
  readonly title: string;
  readonly interval: CalendarEventInterval;
}

const eventAdapter = defineEventAdapter<Meeting>()({
  getId: (meeting) => meeting.id,
  getTitle: (meeting) => meeting.title,
  getInterval: (meeting) => meeting.interval,
  getResourceIds: () => [],
});

type List = ListProjection<Meeting, string, string>;

// Props are getters in Solid: read `props.projection` in the JSX, and don't destructure it.
function Agenda(props: CalendarViewRendererProps<List, ListViewOptions>) {
  const day = (date: Temporal.PlainDate) =>
    date.toLocaleString(props.environment.locale, { dateStyle: "full" });

  return (
    <For each={props.projection.days} fallback={<p>Nothing in these weeks.</p>}>
      {(entry) => (
        <section>
          <h3>{day(entry.date)}</h3>
          <ul>
            <For each={entry.items}>
              {(item) => <li data-event-id={item.event.id}>{item.event.title}</li>}
            </For>
          </ul>
        </section>
      )}
    </For>
  );
}

const listView = defineCalendarView({
  name: "list",
  defaultOptions: { weeks: 2 } as ListViewOptions,
  strategy: {
    getRange: (anchor, environment, options) => getListRange(anchor, environment, options),
    getTitle: (range, environment) => getListTitle(range, environment),
    navigate: (anchor, delta, options) => navigateList(anchor, delta, options),
    project: (input) => projectList(input) as List,
  },
  Renderer: Agenda,
});

export const Calendar = createCalendar<Meeting>()({ eventAdapter, views: [listView] });

export type View = (typeof Calendar.views)[number]["name"];
```

`Root` takes your events and the handler that saves a change, as in React. Events live in a
signal of yours, and the calendar never stores them:

```tsx title="app.tsx"
import type { CalendarProposalDetail, CalendarWeekRules } from "@moltenship/calendar-core";
import { createSignal } from "solid-js";

import { Calendar, type Meeting } from "./calendar";

const timeZone = "Europe/Berlin";
const at = (value: string) =>
  Temporal.PlainDateTime.from(value).toZonedDateTime(timeZone).toInstant();

const seed: readonly Meeting[] = [
  {
    id: "standup",
    title: "Standup",
    interval: { kind: "timed", start: at("2026-10-08T09:00"), end: at("2026-10-08T09:30") },
  },
];

const weekRules: CalendarWeekRules = { firstDay: 1, minimalDays: 4, weekend: [6, 7] };

// A title an agent sent with `createEvent` or `updateEvent`. A person's gesture sends none.
function titleFrom(detail: CalendarProposalDetail): string | undefined {
  const title = detail.fields?.title;
  return typeof title === "string" && title.trim() !== "" ? title.trim() : undefined;
}

export function App() {
  const [meetings, setMeetings] = createSignal<readonly Meeting[]>(seed);

  return (
    <Calendar.Root
      label="Team calendar"
      events={meetings()}
      defaultAnchorDate={Temporal.PlainDate.from("2026-10-08")}
      defaultTimeZone={timeZone}
      locale="en-US"
      weekRules={weekRules}
      onEventChange={(change, detail) => {
        const title = titleFrom(detail);
        if (change.cause === "delete") {
          setMeetings((current) => current.filter((meeting) => meeting.id !== change.eventId));
        } else if (change.cause === "create") {
          setMeetings((current) => [
            ...current,
            { id: crypto.randomUUID(), title: title ?? "New meeting", interval: change.proposed },
          ]);
        } else {
          setMeetings((current) =>
            current.map((meeting) =>
              meeting.id === change.eventId
                ? { ...meeting, title: title ?? meeting.title, interval: change.proposed }
                : meeting,
            ),
          );
        }
      }}
    >
      <Calendar.Frame>
        <Calendar.Toolbar>
          <Calendar.PreviousTrigger>Previous</Calendar.PreviousTrigger>
          <Calendar.TodayTrigger>Today</Calendar.TodayTrigger>
          <Calendar.NextTrigger>Next</Calendar.NextTrigger>
          <Calendar.Title />
        </Calendar.Toolbar>
        <Calendar.Viewport>
          <Calendar.ActiveView />
        </Calendar.Viewport>
      </Calendar.Frame>
    </Calendar.Root>
  );
}
```

## What it exports

| Export                                                             | What it is                                                                                                             |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| `createCalendar<TEvent, TResource, TSelection, TFocus>()(options)` | The factory. Takes `eventAdapter`, `views` and `invalidEventPolicy`, as [React's](/docs/api/react#createcalendar) does |
| `defineCalendarView({ name, defaultOptions, strategy, Renderer })` | A view. `Renderer` is a Solid component                                                                                |
| `createStateSelector(source, selector, options?)`                  | An accessor of one value of a store                                                                                    |
| `createCalendarStore(options)`                                     | The [state store](/docs/api/store). The same function `@moltenship/calendar` exports                                   |
| `resolveViewOptions(view, overrides)`                              | A view's options: its `defaultOptions` with a root's `viewOptions` over them                                           |

It also exports the types of all of these, and the state types: `CalendarPublicState`,
`CalendarActions`, `CalendarStore`, `CalendarStateChangeDetail`, `CalendarCommandOptions` and the
others [Primitives](/docs/api/primitives#what-it-exports) lists.

## The factory

`createCalendar` returns the parts and hooks for your record types.

### Parts

| Part              | Renders     | Notes                                                                                      |
| ----------------- | ----------- | ------------------------------------------------------------------------------------------ |
| `Root`            | nothing     | Provides the calendar. Its props are the ones [React's `Root`](/docs/api/react#root) takes |
| `Frame`           | `<section>` | Named by `Root`'s `label`, or by the title without one. An agent finds the calendar here   |
| `Toolbar`         | `<header>`  |                                                                                            |
| `Title`           | `<span>`    | The visible dates, from the view's `getTitle`                                              |
| `PreviousTrigger` | `<button>`  | Needs children or an `aria-label`                                                          |
| `NextTrigger`     | `<button>`  | Needs children or an `aria-label`                                                          |
| `TodayTrigger`    | `<button>`  | Needs children or an `aria-label`                                                          |
| `ViewSwitcher`    | `<select>`  | One option per view. Requires `getViewLabel(name)`                                         |
| `Viewport`        | `<div>`     | Wrapper for the view                                                                       |
| `ActiveView`      | view output | Renders the active view's `Renderer`, or `fallback` if the view isn't registered           |
| `Event`           | children    | Looks up one event by `eventId`. Its children get an accessor of the event as it shows     |
| `Announcer`       | `<div>`     | The live region for keyboard, pointer and undo announcements. Takes `messages`             |

Each part has the `data-calendar-part` attribute React's has, so CSS written for one works for the
other. The parts take the element's own props, in Solid's spelling: `class`, not `className`.

`Root`'s props have the same names, types and defaults as in React, the agent's `label`,
`allowAgentDelete` and `formatAgentEventLabel` included. Pass a signal's value for a prop that
changes: `events={meetings()}`, `view={view()}`.

### Hooks

Call them in a component inside `Root`. Where React's hook returns a value, Solid's returns an
accessor:

| Hook                                      | Returns                                                                                                |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `useCalendarState()`                      | `Accessor` of the six state values                                                                     |
| `useCalendarSelector(selector, options?)` | `Accessor` of one value from the state. Re-runs readers only when it changes by `options.isEqual`      |
| `useCalendarActions()`                    | The actions, as an object. Stable for the root's lifetime                                              |
| `useCalendarMeta()`                       | `Accessor` of the meta: `label`, `environment`, `eventSnapshot`, `views`, `diagnostics`, `ids`, `refs` |
| `useVisibleRange()`                       | `Accessor` of the visible dates, or `null`                                                             |
| `useViewProjection()`                     | `Accessor` of the active view and its projection, or `null`                                            |
| `useCalendarPendingChanges(selector?)`    | `Accessor` of the changes being saved, or of what `selector` picks from them                           |
| `useCalendar()`                           | `{ actions, meta, state }`. `meta` and `state` are getters                                             |

The package also exports the hooks a view is built with. They're the same as
[React's](/docs/api/react#hooks), with an accessor where React returns a value, and they take an
accessor wherever an argument can change:

| Hook                                                                  | Returns                                                                                      |
| --------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `useCalendarKeyboard(options?)`                                       | A ref for the element around the view's cells. Binds `keydown` and `focusout` on it          |
| `useRovingFocus(target, options?)`                                    | The props for one focusable day, slot or event: `tabIndex`, `onFocus` and `ref`. Spread them |
| `useCalendarFocus(selector?)`, `useCalendarSelection(selector?)`      | `Accessor` of the focus or the selection, or of what `selector` picks from it                |
| `useCalendarInteraction(selector?)`                                   | `Accessor` of the keyboard gesture in progress, or `null`                                    |
| `useCalendarPointer(options)`                                         | A ref for the element around the view's days. Turns drags into proposals                     |
| `useCalendarDraft()`, `useCalendarDraftReporter()`                    | `Accessor` of the pointer gesture's draft, and the function a pointer layer reports it to    |
| `useDraftBusy(...)`, `useBusyResources(...)`                          | `Accessor` of whether a draft overlaps busy time, and of the busy resources                  |
| `useCalendarAnnouncer()`                                              | The announcer `useCalendarPointer` takes, which speaks through `Announcer`                   |
| `useCalendarHistory(history, options?)`                               | `Accessor` of the undo stack, `canUndo`, `canRedo`, `undo()` and `redo()`                    |
| `useCalendarHistoryShortcuts(controls, options)`                      | Nothing. Binds Mod+Z to undo, and Shift+Mod+Z or Ctrl+Y to redo, inside `scope`              |
| `useNow(options?)`                                                    | `Accessor` of the current instant, or `null` on the server without `now`                     |
| `useVisibleResources()`, `useResourceExpansion()`                     | `Accessor` of the resource rows, and the controls that expand and collapse them              |
| `useResourceStatus(resourceId, at?)`                                  | `Accessor` of a resource's availability and busy state, or `null`                            |
| `useCalendarAvailability()`, `useClosedDates(range)`                  | `Accessor` of the availability snapshot, and of the closed dates in `range`                  |
| `useTimeGridAvailability(columns, id?)`, `useTimelineAvailability(…)` | `Accessor` of the closed time per column, or per resource row                                |
| `useCalendarAnnotations()`, `useTimeGridAnnotations(columns)`         | `Accessor` of the annotations, and of those laid out on a time grid                          |
| `useAnchorDateRequests(onRequest)`                                    | Nothing. Calls `onRequest` when the calendar asks a scrolling view to show a date            |

`eventIdAttributes(id)` and `resourceIdAttributes(id)` return the data attributes the pointer layer
reads on an event and a resource, so a numeric ID stays a number.

```tsx title="status.tsx"
import { Calendar } from "./calendar";

// Render it inside <Calendar.Root>.
export function Status() {
  const state = Calendar.useCalendarState();
  const range = Calendar.useVisibleRange();
  const view = Calendar.useCalendarSelector((current) => current.view);
  const saving = Calendar.useCalendarPendingChanges((changes) => changes.size > 0);
  const actions = Calendar.useCalendarActions();

  return (
    <p>
      {view()} from {range()?.start.toString()}, anchored on {state().anchorDate.toString()}
      {saving() ? ", saving" : ""}
      <button type="button" onClick={() => actions.navigateToday()}>
        Today
      </button>
    </p>
  );
}
```

## Keyboard and dragging in a view

A view gets keyboard navigation from three pieces, as in React:

- **`getSpatialNavigation`** on the strategy says where each key moves focus. Reuse
  `monthSpatialNavigation`, `listSpatialNavigation` or another from `@moltenship/calendar-core`.
- **`useCalendarKeyboard()`** returns a ref for the element around the view's cells.
- **`useRovingFocus(target)`** returns the props for each day, slot and event that takes focus.
  The view has one tab stop.

`useCalendarPointer(options)` returns another ref for the same element. It turns a drag on an
event into a move, a drag on an element with `data-resize` into a resize, and a drag across days
into a create, and proposes each through the options' `onPropose`. The hook passes `options` to
`attachCalendarPointer` untouched, so [Pointer layer](/docs/api/changes#pointer-layer) documents
every option. Give one element both refs with `ref={[keyboard, pointer]}`.

```tsx title="month.tsx"
import {
  getMonthRange,
  getMonthTitle,
  monthSpatialNavigation,
  navigateMonth,
  projectMonth,
  type DayGridSegment,
  type MonthDay,
  type MonthProjection,
} from "@moltenship/calendar-core";
import {
  defineCalendarView,
  eventIdAttributes,
  useCalendarAnnouncer,
  useCalendarDraftReporter,
  useCalendarKeyboard,
  useCalendarPointer,
  useRovingFocus,
  type CalendarViewRendererProps,
} from "@moltenship/calendar-solid";
import { For } from "solid-js";

import type { Meeting } from "./calendar";

type Month = MonthProjection<Meeting, string, string>;

function Day(props: { readonly day: MonthDay; readonly column: number }) {
  // An accessor, so the cell registers again when a new projection hands it a new day.
  const roving = useRovingFocus(() => ({ date: props.day.date, kind: "day" }));
  return (
    <button
      {...roving}
      type="button"
      data-date={props.day.date.toString()}
      style={{ "grid-column": `${props.column + 1}` }}
    >
      {props.day.date.day}
    </button>
  );
}

function Chip(props: {
  readonly date: Temporal.PlainDate;
  readonly segment: DayGridSegment<Meeting, string, string>;
}) {
  const roving = useRovingFocus(
    () => ({ date: props.date, eventId: props.segment.event.id, kind: "event" }),
    () => ({ days: props.segment.span }),
  );
  return (
    <button
      {...roving}
      {...eventIdAttributes(props.segment.event.id)}
      type="button"
      style={{
        "grid-column": `${props.segment.column + 1} / span ${props.segment.span}`,
        "grid-row": `${props.segment.lane + 2}`,
      }}
    >
      {props.segment.event.title}
      <span data-resize="end" aria-hidden="true" />
    </button>
  );
}

function MonthGrid(props: CalendarViewRendererProps<Month, undefined>) {
  const keyboard = useCalendarKeyboard();
  // A drag speaks through the root's Announcer, and its draft shows in useCalendarDraft.
  const announcer = useCalendarAnnouncer();
  const onPreview = useCalendarDraftReporter();
  const pointer = useCalendarPointer(() => ({
    announcer,
    check: props.actions.checkEventChange,
    disabled: props.isReadOnly,
    events: props.events,
    onPreview,
    onPropose: props.actions.proposeEventChange,
    timeZone: props.environment.timeZone,
  }));
  return (
    <div ref={[keyboard, pointer]}>
      <For each={props.projection.weeks} keyed={(week) => week.range.start.toString()}>
        {(week) => (
          <div style={{ display: "grid", "grid-template-columns": "repeat(7, 1fr)" }}>
            <For each={week().days} keyed={(day) => day.date.toString()}>
              {(day, index) => <Day day={day()} column={index()} />}
            </For>
            {/* Keyed by event: a dropped chip keeps its element, and its focus. */}
            <For each={week().segments} keyed={(segment) => segment.event.id}>
              {(segment) => <Chip date={week().days[segment().column]!.date} segment={segment()} />}
            </For>
          </div>
        )}
      </For>
    </div>
  );
}

export const monthView = defineCalendarView({
  name: "month",
  strategy: {
    getRange: (anchor, environment) => getMonthRange(anchor, environment),
    getSpatialNavigation: monthSpatialNavigation,
    getTitle: (range, environment) => getMonthTitle(range, environment),
    navigate: (anchor, delta) => navigateMonth(anchor, delta),
    project: (input) => projectMonth(input) as Month,
  },
  Renderer: MonthGrid,
});
```

The keys are the ones [Keyboard](/docs/accessibility#keyboard) lists. Space picks up the focused
event, or starts a new one on the focused day, arrow keys move it, and Enter or Space drops it. A
pointer drags the event, its `data-resize` handle, or across empty days. Both stop when `Root` has
no `onEventChange` or is `readOnly`. Each gesture's change runs your policies and `onEventChange`,
as every other change does.

Render `<Calendar.Announcer messages={messages} />` inside `Root` so a screen reader hears each
gesture. The package ships no text: the registry's `calendar/announcements.ts` has an English set,
and [Announcements](/docs/accessibility#announcements) describes the messages.

## Undo and redo

`useCalendarHistory(history)` binds a history from `createEventHistory` to the calendar, and
`useCalendarHistoryShortcuts` adds the keyboard shortcuts. Record every result in `Root`'s
`onEventChangeResult`:

```tsx title="history.tsx"
import { createEventHistory } from "@moltenship/calendar-core";
import { useCalendarHistory, useCalendarHistoryShortcuts } from "@moltenship/calendar-solid";

import { Calendar, type Meeting } from "./calendar";

// One per calendar. Pass `onEventChangeResult={(result, detail) => changes.record(result, detail)}`
// to Root.
export const changes = createEventHistory<Meeting, string, string>();

// Render it inside <Calendar.Root>.
export function HistoryButtons() {
  const controls = useCalendarHistory(changes);
  const meta = Calendar.useCalendarMeta();
  useCalendarHistoryShortcuts(controls, () => ({ scope: meta().refs.frame }));
  return (
    <>
      <button type="button" disabled={!controls().canUndo} onClick={() => void controls().undo()}>
        Undo
      </button>
      <button type="button" disabled={!controls().canRedo} onClick={() => void controls().redo()}>
        Redo
      </button>
    </>
  );
}
```

To undo a create, the history needs the ID your app gave the new event: pass `createdEventId` to
`createEventHistory`, as [Creates and deletes](/docs/undo-redo#creates-and-deletes) shows.
`messages` in the hook's options speak each undo and redo through `Announcer`.

## Server rendering

`Root`, the parts and every hook render on the server with `@solidjs/web`'s `renderToString`, and
hydrate without a mismatch. On the server the calendar doesn't read the clock, the host time zone
or `window`. Without `now`, `useNow` gives `null` on the server and while hydrating, and the tab
stop is the view's entry, which is today only when `now` is set. A store with `getServerSnapshot`
renders that snapshot on the server and while hydrating. The keyboard and pointer refs attach
nothing until the page hydrates.

## Differences from React

| In React                                     | In Solid                                                                                          |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Hooks return values                          | Hooks return accessors: `state().view`, not `state.view`                                          |
| `useCalendar()` returns plain objects        | `meta` and `state` are getters. Read them in JSX, a memo or an effect, and don't destructure them |
| A `Renderer` gets props you can destructure  | A `Renderer`'s props are getters: `props.projection`, read where it's used                        |
| `meta.refs` holds React refs                 | `meta.refs` holds accessors: `meta().refs.viewport()`                                             |
| `useCalendarKeyboard()` returns handlers     | It returns a ref, which binds `keydown` and `focusout` on the element itself                      |
| `useRovingFocus` listens for `focusin`       | It listens for `focus`, so a focus handler of yours hears `"focus"`                               |
| `Calendar.Event`'s children get a value      | They get an accessor, and stay rendered while the event changes                                   |
| A state change is visible on the next render | An accessor has the new value once Solid flushes: a microtask later, or after `flush()`           |
| `@moltenship/calendar` is the one package    | `@moltenship/calendar-solid` and `@moltenship/calendar-core`                                      |
| The bridge is `@ui-sdk/react/agent`          | The bridge is `@ui-sdk/solid/agent`                                                               |

What doesn't differ: the [state model](/docs/concepts/state), controlled and uncontrolled props,
[change handlers](/docs/concepts/state#what-a-handler-hears), `onEventChange` and
`onEventChangeResult`, [policies](/docs/api/changes), pending changes, and every agent action.

## A store outside Root

`createStateSelector` reads one value of a store as an accessor, for a component outside `Root`:

```tsx title="store.tsx"
import { createCalendarStore, createStateSelector } from "@moltenship/calendar-solid";

import type { View } from "./calendar";

export const store = createCalendarStore<View>({
  defaultView: "list",
  defaultAnchorDate: Temporal.PlainDate.from("2026-10-08"),
  defaultTimeZone: "Europe/Berlin",
});

// An accessor of one value, for a component outside <Calendar.Root store={store}>.
export function AnchorDate() {
  const anchorDate = createStateSelector(store, (state) => state.anchorDate, {
    isEqual: (a, b) => a.equals(b),
  });
  return <time>{anchorDate().toString()}</time>;
}
```

Pass the store to `Root` as `store={store}`, and `store.actions.setAnchorDate(date)` moves the
calendar from anywhere. The store's view type has to be the calendar's, and so do its selection
and focus types if you changed them. A calendar without resources takes a store made without the
resource ID type, as here. [State store](/docs/api/store) has the rest.

## Agents

The actions an agent can call are the primitives package's, so a Solid calendar offers the same
ones as a React calendar, with the same inputs, results and errors. See the
[agent reference](/docs/agents/reference). The bridge
comes from ui-sdk's Solid package.

```ts title="agent.ts"
import { createAgent } from "@ui-sdk/solid/agent";

// One bridge for the page, created before the app renders.
export const agent = createAgent({
  // Reading, navigation and changes run. A delete doesn't, until your app asks the person.
  allow: (step) => step.action !== "deleteEvent",
});

export async function moveStandup() {
  const outcome = await agent.act({
    steps: [
      {
        ref: "Team calendar",
        action: "moveEvent",
        // Every action takes one object.
        args: [{ eventId: "standup", start: "2026-10-09T11:00" }],
      },
    ],
  });
  if (!outcome.ok) {
    return outcome.error?.message ?? "failed";
  }
  // The change the calendar made of the step: `{ changeId, cause, eventId, proposed, status }`.
  return JSON.stringify(outcome.steps[0]?.result);
}
```

With the calendar above, `moveStandup()` calls your `onEventChange` with `detail.input` equal to
`"agent"`, the standup shows on October 9, and the function returns the change:

```json
{
  "cause": "move",
  "changeId": "change-1",
  "eventId": "standup",
  "proposed": {
    "end": "2026-10-09T11:30:00+02:00",
    "kind": "timed",
    "resourceIds": [],
    "start": "2026-10-09T11:00:00+02:00"
  },
  "status": "saved"
}
```

`status` is `"saved"` because this handler saves synchronously. A handler that returns a promise
gives `"saving"`, and the agent reads how it ended with `getChange`: see
[What a step returns](/docs/agents#what-a-step-returns).

- **Create the bridge before the app renders.** Import its module before the one that calls
  `render`.
- **Give `Root` a `label` and render `Calendar.Frame`.** An agent finds the calendar by the label,
  and a calendar without a frame isn't listed.
- **Read `detail.fields` in `onEventChange`.** An agent's `createEvent` and `updateEvent` send the
  title there, and the calendar doesn't store it for you. The `App` above does this with
  `titleFrom`. See [Save what the agent sent](/docs/agents/connect#save-what-the-agent-sent).
- **A calendar has `deleteEvent` only when `Root` has `allowAgentDelete`.** Without it the action
  isn't among the calendar's, a step that asks for it fails whatever `allow` returns, and a delete
  an agent causes by pressing a button of yours is refused.

The [Agents in your app](/docs/agents) guides show React. The bridge's API (`createAgent`, `snapshot`, `act`,
`agentTools`, `registerTools`) and everything about the calendar's actions carry over; only the
import path changes.
