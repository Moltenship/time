Everything on this page is exported from `@moltenship/calendar`. [Interactions](/docs/interactions)
explains how the pieces fit together.

## Proposals

`actions.proposeEventChange(proposal)` takes one of these:

```ts
type CalendarEventProposal =
  | { cause: "create"; proposed: Placement; event?: TEvent }
  | {
      cause: "move" | "resize-start" | "resize-end" | "update";
      eventId: EventId;
      proposed: Placement;
    }
  | { cause: "delete"; eventId: EventId };
```

A placement is a [range](/docs/api/events#ranges) (`kind`, `start`, `end`) plus optional
`resourceIds`. Leaving out `resourceIds` keeps the event's current resources. A create may carry
one of your records as `event`, such as a deleted event an
[undo](/docs/undo-redo#creates-and-deletes) restores; the change hands it on.

## Changes

`onEventChange` and policies receive a `CalendarEventChange`:

| Field      | `create`                                 | `move`, `resize-*`, `update` | `delete`             |
| ---------- | ---------------------------------------- | ---------------------------- | -------------------- |
| `cause`    | `"create"`                               | the cause                    | `"delete"`           |
| `id`       | a change ID                              | a change ID                  | a change ID          |
| `eventId`  | `null`                                   | the event's ID               | the event's ID       |
| `event`    | `null`, or the record the create carries | your record                  | your record          |
| `original` | `null`                                   | the placement before         | the placement before |
| `proposed` | the new placement                        | the new placement            | `null`               |
| `warnings` | reasons `warn` policies flagged, if any  | the same                     | the same             |

Placements in a change always include `resourceIds`. `original` is what the user saw, including any
change still pending for the same event. `warnings` is absent when no policy flagged the change.

## Results

`proposeEventChange` resolves with `{ status: "committed", change }` or
`{ status: "rejected", reason, change?, error? }`. It never rejects. The
[reasons](/docs/interactions#changing-events-from-your-own-ui) are listed on the Interactions page.
`Root`'s `onEventChangeResult` gets the same result for every proposal, with the detail it was
proposed with (`CalendarProposalDetail`): `{ input: "pointer" | "keyboard" | "api" }`, and
`history: "undo" | "redo"` on an event history's inverse. A detail that names no input reads
`{ input: "api" }`.

While a proposal is on its way, `useCalendarPendingChanges` lists it as a `CalendarPendingChange`,
`{ change, phase }`, with `phase` one of `"validating"`, `"saving"` and `"awaiting-events"`. See
[pending changes](/docs/interactions#across-the-calendar).

## Event history

`createEventHistory(options?)` records committed changes and undoes and redoes them through the
pipeline. Its members are plain functions: `record(result, detail)` for `onEventChangeResult`,
`undo(context)` and `redo(context)`, `clear()`, `getSnapshot()` and `subscribe(listener)`. The
context is `{ getEvents, propose, input?, whenSettled? }`. See [Undo and redo](/docs/undo-redo)
for the options, the steps (`EventHistoryStep`), the outcomes (`EventHistoryOutcome`) and the
snapshot (`EventHistorySnapshot`), and `useCalendarHistory` binds a history to a `Root`.

## Policies

```ts
type CalendarPolicy = (
  change: CalendarEventChange,
  context: { events: EventSnapshot; timeZone: string; availability?: AvailabilitySnapshot },
) => Decision | Promise<Decision>;

type Decision =
  | { type: "accept" }
  | { type: "adjust"; proposed: Placement }
  | { type: "reject"; reason: string }
  | { type: "warn"; reason: string };
```

`warn` accepts the change and adds `reason` to its `warnings`. `context.availability` holds the
root's working hours, for `availabilityPolicy`. `context.events` includes pending changes, so a
policy sees the calendar as the user does. A policy
that throws rejects the change with the reason `policy-error`.

| Policy                                      | Behaviour                                                                                                                                                                                                                                                                                                                                                          |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `snapPolicy(increment)`                     | Rounds timed and floating changes to a wall-clock grid in the calendar's time zone, such as `{ minutes: 15 }`. Moves keep their length; resizes snap only the dragged edge. All-day changes pass through. The increment must divide an hour or a day evenly.                                                                                                       |
| `minimumDurationPolicy(minimum)`            | Lengthens timed and floating changes shorter than `minimum`. Resizing the start moves the start earlier; anything else moves the end later.                                                                                                                                                                                                                        |
| `boundsPolicy({ start, end })`              | Rejects changes that reach outside `[start, end)`, with the reason `out-of-bounds`. Both bounds are optional instants.                                                                                                                                                                                                                                             |
| `readOnlyPolicy()`                          | Rejects changes to events whose adapter `isReadOnly` returns `true`, with the reason `read-only`. `Root` runs it before your policies.                                                                                                                                                                                                                             |
| `availabilityPolicy({ mode })`              | Rejects a change outside working hours, with the reason `outside-availability`, or with `mode: "warn"` saves it with that warning. See [Availability](/docs/availability#keep-changes-inside).                                                                                                                                                                     |
| `conflictPolicy({ mode, getResourceMode })` | Rejects a change that makes a busy event overlap another busy event on one of its resources, with the reason `resource-conflict`; with `mode: "warn"` saves it with that warning, and with `"allow"` as it is. `getResourceMode` gives a resource its own mode; the strictest decides. Deletes always pass. See [Availability](/docs/availability#double-booking). |
| `readOnlyResourcesPolicy(isReadOnly)`       | Rejects creating, deleting, or changing the time of an event on a resource `isReadOnly(resourceId)` marks, and adding or removing that resource, with the reason `read-only-resource`.                                                                                                                                                                             |

## Placement helpers

These build placements for proposals, with the same wall-clock rules the built-in gestures use.

| Function                                                                      | Returns                                                                                                                                           |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `eventPlacement(normalizedEvent)`                                             | The placement of an event from the snapshot                                                                                                       |
| `moveEventPlacement(placement, delta, { timeZone })`                          | The placement moved by a wall-clock delta, such as `{ days: 1, minutes: -30 }`. A 09:00 event moved by a week stays at 09:00 across a DST change. |
| `resizeEventPlacement(placement, edge, delta, { timeZone, minimumDuration })` | One edge moved, keeping at least `minimumDuration` (15 minutes by default; all-day events keep a day)                                             |
| `createEventPlacement(anchor, focus, resourceIds)`                            | A placement covering two ranges of the same kind, such as the first and last slot of a drag                                                       |
| `toAllDayPlacement(placement, { timeZone })`                                  | The dates a placement touches, as an all-day placement                                                                                            |
| `toTimedPlacement(placement, start, duration)`                                | A timed placement starting at a `Temporal.ZonedDateTime`                                                                                          |

For example, this moves an event to the same time on the next day:

`createEventTransactions` and `applyEventOverlay` are the engine `Root` uses to run proposals and
draw pending changes. You only need them to handle changes outside React. The engine's
`getPending()` returns the pending placements `applyEventOverlay` draws, and `getPendingChanges()`
the changes `useCalendarPendingChanges` reads.

## Pointer layer

`useCalendarPointer(options)` returns a ref for the element that contains a view's days, and turns
drags inside it into proposals. `attachCalendarPointer(element, getOptions)` does the same without
React and returns a cleanup function. Both come from `@moltenship/calendar-dnd`, which
`@moltenship/calendar` re-exports.

While a gesture runs, the region has `data-interaction="move"`, `"resize"`, or `"create"`, and the
event being dragged has `data-dragging`. Preview elements have `data-calendar-ghost="event"` or
`"range"`, and `data-invalid` or `data-warning` when `check` says a policy would reject or flag the
drop. Range previews read `--calendar-ghost-background` and `--calendar-ghost-radius`, event
previews `--calendar-ghost-shadow` and `--calendar-ghost-opacity`, and both
`--calendar-ghost-z-index`.
