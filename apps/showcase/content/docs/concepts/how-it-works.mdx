## Packages

```text
@moltenship/calendar                  what you import: everything below
├── @moltenship/calendar-react        Root, components, hooks, state
├── @moltenship/calendar-dnd          drag, resize, and create inside views
├── @moltenship/calendar-core         adapters, validation, snapshots, queries, changes
└── @moltenship/calendar-temporal     ranges, day boundaries, DST helpers
```

`calendar-react` and `calendar-dnd` build on `calendar-core`, which builds on `calendar-temporal`. `calendar-core` and
`calendar-temporal` don't use React or the DOM, so they also run on a server or in a worker.

Two more packages stand apart from `@moltenship/calendar`: `@moltenship/calendar-recurrence` expands
recurring events into ordinary events (it builds on core, Temporal and `ics`), and `@moltenship/ics`
parses iCalendar text with no dependencies.

| Package                           | Use it when                                                                                           |
| --------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `@moltenship/calendar`            | Almost always. It includes `calendar-core`, `calendar-temporal`, `calendar-react` and `calendar-dnd`. |
| `@moltenship/calendar-core`       | You want to validate or query events in code that never loads React.                                  |
| `@moltenship/calendar-temporal`   | You only need the date and time zone helpers.                                                         |
| `@moltenship/calendar-react`      | Rarely. `@moltenship/calendar` already includes everything in it.                                     |
| `@moltenship/calendar-recurrence` | Your events repeat. See [Recurring events](/docs/concepts/recurrence).                                |
| `@moltenship/ics`                 | You read iCalendar feeds or files. See [ICS](/docs/api/ics).                                          |

`@moltenship/calendar` has no `"use client"` directive of its own, so a Server Component can import
its core and Temporal helpers. The React parts and the pointer layer keep their client boundary.

Import from the package name only. The packages export nothing else besides `./package.json`, so a
path such as
`@moltenship/calendar-core/src/events` doesn't resolve.

## From events to the screen

1. You pass `events` to `Root`.
2. `Root` runs each record through your adapter, validates it, and builds a **snapshot**: a frozen,
   indexed copy of your events.
3. `Root` asks the active view's strategy for the visible dates, then calls its `project` function
   with the snapshot. The result is the view's **projection**: the events it needs, in the shape it
   needs.
4. `ActiveView` renders the view's `Renderer` with that projection.
5. Buttons and your own controls call actions such as `navigateNext` or `setView`. The calendar
   updates uncontrolled state itself and sends controlled changes to your handlers. A new date or
   view means a new range and a new projection.

Steps 2 and 3 only run again when their inputs change. A new array with the same records in the same
order reuses the snapshot. A changed array is read again through the adapter, except records with an
unchanged `getRevision` value; if every record comes out the same, the interval indexes are kept.

## Using the engine without React

Snapshots work anywhere. This finds the meetings in a time range using `calendar-core` and
`calendar-temporal` directly:

```ts
import { createEventSnapshotCache } from "@moltenship/calendar-core";
import { instantInterval } from "@moltenship/calendar-temporal";

const snapshots = createEventSnapshotCache(eventAdapter);
const snapshot = snapshots.getSnapshot(meetings);

const morning = snapshot.queryTimed(
  instantInterval(
    Temporal.Instant.from("2026-10-08T06:00:00Z"),
    Temporal.Instant.from("2026-10-08T10:00:00Z"),
  ),
);

morning.map((meeting) => meeting.title); // ["Standup"]
```

`eventAdapter` and `meetings` are the ones from the [Quick start](/docs/quick-start). The
[snapshot reference](/docs/api/events#snapshots) lists every query.
