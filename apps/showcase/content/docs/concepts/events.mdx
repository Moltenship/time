title: Events and adapters

Time has no event class of its own. You pass an array of your own records to `Root`, and an
**adapter** tells Time how to read each one: its ID, title, time range, and the resources it belongs
to.

<include meta='title="bookings.tsx"'>../../examples/bookings.tsx#adapter</include>

`defineEventAdapter<Booking>()` is called twice on purpose. The first call fixes the record type,
and the second infers the ID types from your accessors. Here `booking-${number}` stays
`booking-${number}` everywhere Time hands an ID back to you, so you never cast.

`getRevision`, `isReadOnly` and `isBusy` are optional. The [adapter reference](/docs/api/events#adapter)
lists every field.

## Time ranges

`getInterval` returns one of three kinds of range. Pick the one that matches what the event means:

| `kind`       | `start` and `end`        | Use it for                                                      |
| ------------ | ------------------------ | --------------------------------------------------------------- |
| `"timed"`    | `Temporal.Instant`       | Meetings and calls: exact moments, shown in the calendar's zone |
| `"all-day"`  | `Temporal.PlainDate`     | Holidays and vacations: whole dates, the same in every zone     |
| `"floating"` | `Temporal.PlainDateTime` | Wall-clock times with no zone, like "gym at 7:00"               |

The end is always exclusive. A one-day all-day event on October 8 has `end` set to October 9.
[Time and time zones](/docs/concepts/time) covers this in detail.

## IDs

Event and resource IDs are non-empty strings or finite numbers. To check untrusted input before
it reaches the calendar, use `isEventId` and `isResourceId`:

```ts
import { isEventId } from "@moltenship/calendar";

isEventId("booking-12"); // true
isEventId(""); // false
isEventId(Number.NaN); // false
```

## Resources

Resources are what events are assigned to: rooms, people, equipment. Pass your own resource records
(anything with an `id`) to `Root` as `resources`, and return their IDs from `getResourceIds`. An
event can belong to no resource, one, or several.

Views can then filter by resource with `snapshot.eventsForResource(roomId)` or
`snapshot.queryTimed(range, { resourceIds: [roomId] })`. See [snapshot queries](/docs/api/events#queries).

## Changing events

Time never edits, saves, or fetches your events. When your data changes, update your own state and
pass a new array. To fetch only the dates on screen, load the `loadRange` that
[`onVisibleRangeChange`](/docs/views/scrolling#loading-events-as-you-scroll) reports.

Treat your records as immutable: change a record by replacing it with a new object. Time compares
the array item by item, so a new array with the same records in the same order counts as unchanged,
even if you build it inline with `filter` or `map`. When the array does change, Time reads every record again
through the adapter; if every record comes out the same, in the same order, it keeps its interval indexes. With
`getRevision`, a record whose revision is unchanged is skipped after `getId` and `getRevision`. The [performance guide](/docs/guides/performance)
explains how to make the most of that.

## Events from an external store

`events` also takes a **source**: an object with `getSnapshot`, `getServerSnapshot` and
`subscribe`, the shape React's `useSyncExternalStore` reads. Use one when your events live outside
React and change often, as in a store a websocket or a sync engine updates, or a Zustand-like
store. `Root` subscribes to the source itself, so an update renders the calendar, not the component
that renders `Root`. With a Zustand store:

```tsx
import type { CalendarEventSource } from "@moltenship/calendar";

// At module scope, so the source stays the same object.
const bookingSource: CalendarEventSource<Booking> = {
  getSnapshot: () => useBookings.getState().bookings,
  getServerSnapshot: () => useBookings.getInitialState().bookings,
  subscribe: useBookings.subscribe,
};

<BookingCalendar.Root events={bookingSource} {...otherProps} />;
```

- `getSnapshot` returns the same array until the events change. Don't filter or map inside it: a
  new array on every call looks like a change every time, and React renders in a loop.
- `getServerSnapshot` returns the events the server rendered with. The server and hydration read
  it, then `Root` shows `getSnapshot`'s events and subscribes. Without server rendering, return the
  store's initial events.
- Keep the source stable, at module scope or in `useState`. A new source object subscribes again.

Everything else works as with an array: records are compared item by item and read through your
adapter, a saved change stays [pending](/docs/interactions#pending-changes) until the source's
events next change, and you can switch between an array and a source. A busy source changes
often, so write a saved change into the store before your handler's promise resolves: otherwise
the source's next update, even one about other events, decides where the event is. React renders a source's
updates right away, as it does for any external store; to update in a transition, keep the events
in state and pass the array.

## Invalid records

By default, an invalid record is skipped and reported. The rest of the calendar keeps working.
Reasons include a missing or duplicate ID, an end that isn't after the start, a range of the wrong
Temporal type, or an adapter function that throws.

Reports show up in `meta.diagnostics` and in the `onDiagnosticsChange` callback on `Root`:

<include meta='title="bookings.tsx"'>../../examples/bookings.tsx#diagnostics</include>

Pass `reportDiagnostics` as `onDiagnosticsChange`. Time calls it after mount and again whenever the
list changes; an inline function works too.

To reject bad input instead, pass `invalidEventPolicy: "throw"` to `createCalendar`.
Time then throws an `InvalidCalendarEventSnapshotError` during render, with every problem listed on
its `issues` property. Catch it with an error boundary.

## Records in Time's own shape

If you're starting from scratch, you can store events in Time's built-in shape (`CalendarEvent`: an
`id`, `title`, `kind`, `start`, `end`, optional `resourceIds`, and your own `data`) and use
`createCanonicalEventAdapter()` instead of writing an adapter.
