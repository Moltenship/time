---
title: Migrating to 2.0
description: What changes between Time 1.x and 2.0, and what to do about each change.
---

2.0 rebuilds the calendar's parts on [ui-sdk](https://ui-sdk.dev). With it, an
[agent](/docs/agents) can call the calendar's actions, and the calendar has a second framework,
Solid, with [docs of its own](/docs/solid). The engine didn't move: dates, time zones, recurrence, layouts, transactions and policies work as they did.

For most apps the upgrade is two more packages to install. The rest of this page is for code that
names the types 2.0 widened.

<Callout type="warn" title="2.0 is a pre-release">
  Its API can still change before 2.0.0, and ui-sdk is in beta. Stay on 1.x if you need a stable API
  today: it keeps the shape it has.
</Callout>

## In short

| Change                                                                                  | Do this                                                                            | Who it affects                                                                  |
| --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `@ui-sdk/core` and `@ui-sdk/react` are peer dependencies                                | [Install them](#install-the-new-peer-dependencies)                                 | Everyone                                                                        |
| `CalendarInputMethod` has a fourth value, `"agent"`                                     | [Handle it](#handle-the-agent-input)                                               | Code that switches on `detail.input`                                            |
| `onEventChange` and policies get the proposal's detail, with `fields`                   | [Check handlers with a second parameter](#handlers-and-policies-hear-who-proposed) | Handlers with an optional second parameter, and code that calls a typed handler |
| The toolbar parts and the frame render a `data-slot` attribute                          | [Check selectors on `data-slot="calendar"`](#the-parts-have-data-slot)             | Apps with shadcn's date picker, or such CSS                                     |
| State handlers hear `reason`, `source`, `event` and can `cancel()`                      | Nothing. [Use it](#state-handlers-hear-why-and-who)                                | Code that builds a `detail` by hand, in tests                                   |
| Actions take options last                                                               | [Wrap an action used as an event handler](#actions-take-options)                   | Code such as `onClick={actions.navigateNext}`                                   |
| `Root` has `label`, `allowAgentDelete` and `formatAgentEventLabel`                      | [Name your calendar](#name-the-calendar)                                           | Apps that want agents, or a fixed name                                          |
| The store and state types moved to `@moltenship/calendar-primitives`                    | Nothing: [the old imports still work](#new-packages)                               | Nobody                                                                          |
| `useCalendarPointer` moved to `@moltenship/calendar-react`                              | [Import it from there](#the-pointer-hook-moved)                                    | Code that imports it from `@moltenship/calendar-dnd`                            |
| The registry's controls and popups come from a new item, `calendar-ui`, without Base UI | [Add the registry's items again](#add-the-registrys-items-again)                   | Apps with the Tailwind items from the registry                                  |

What didn't change: the engine, what the registry's views do, the `data-calendar-part` attributes
and the other attributes your CSS and tests target, the keyboard model, and every hook's name and return
value. The parts gained one attribute, [`data-slot`](#the-parts-have-data-slot).

- **`react-dom` is needed too.** `@ui-sdk/react` has it as a peer dependency. A React app on the web
  already has it.
- **Install the 2.0 version of every `@moltenship/*` package you use.** They share one version,
  and a 1.x package beside a 2.0 one brings a second copy of the engine.
- **`@moltenship/calendar-testing` has the same two peers.** A project that tests with it needs
  nothing more once the app has them.
- **`shadcn add` installs them only if they're missing.** The registry's `calendar-ui` item lists
  the ui-sdk packages without a version, so an app that already has them keeps its own. Install
  the version the calendar asks for yourself.
- **Keep one copy of `@ui-sdk/core`.** The calendar and an [agent bridge](/docs/agents/connect)
  find each other through it. Your package manager keeps one as long as every `@ui-sdk/*` package
  is on the same version; `pnpm why @ui-sdk/core` shows whether it did.

The calendar takes `@ui-sdk/core` and `@ui-sdk/react` from `0.1.0-beta.16` on, within the 0.1
line.

## Handle the agent input

`CalendarInputMethod` was `"pointer" | "keyboard" | "api"`. It's now
`"pointer" | "keyboard" | "api" | "agent"`. The value is the `input` of the detail that
`onEventChangeResult` gets, and of a history step.

Code that only compares, such as `detail.input === "keyboard"`, keeps working. A `switch` that
TypeScript checks for every case stops compiling until it has the fourth:

<include meta='title="input-label.ts"'>../examples/migrating-input.ts</include>

No agent proposes anything until your app creates a bridge, so `"agent"` never arrives in an app
that doesn't opt in. In one that does, `"agent"` is the input of everything an agent's step
causes. That includes a `proposeEventChange` your own button's handler makes when an agent
presses the button, which a person's click still reports as `"api"`.

An [event history](/docs/undo-redo) records every input by default, and now that includes an
agent's. To leave an agent's changes out of undo, list the inputs you want:

<include meta='title="history.ts"'>../examples/migrating-history.ts</include>

## Handlers and policies hear who proposed

In 1.x only `onEventChangeResult` got the proposal's detail. In 2.0 `onEventChange` gets it as a
second argument, and a policy as `detail` in its second argument. Handlers that take one argument
are unchanged.

<include meta='title="saving.tsx"'>../examples/migrating-saving.tsx</include>

Two kinds of code do change:

- **A handler with a second parameter of its own.** 1.x called `onEventChange` with the change
  alone. A function passed directly, as `onEventChange={save}` where `save` is
  `(change, options?) => …`, now receives the detail as `options`. TypeScript reports it when the
  two types differ, and stays silent when `options` is loose enough to take a detail. Wrap the
  call: `onEventChange={(change) => save(change)}`.
- **Code that calls a typed handler.** `CalendarEventChangeHandler` now has two parameters, and
  `detail` is required. A test or a wrapper that calls such a handler with one argument stops
  compiling. Pass a detail: `handler(change, { input: "api" })`.

`applyChange` and `calendar.tsx` are the ones from [Connect an agent](/docs/agents/connect#name-the-calendar)
and the [Quick start](/docs/quick-start).

The detail has a new optional member, `fields`: what a change says beside where the event goes.
An agent's `createEvent` and `updateEvent` put the title there, and whatever else the agent sent.
A person's gestures send none, so a handler that ignores `detail` saves a person's changes as it
did. It saves an agent's too, but without the title, which is why `applyChange` above takes the
detail. See [Save what the agent sent](/docs/agents/connect#save-what-the-agent-sent).

`actions.checkEventChange(proposal, detail?)` takes the detail as well, so a preview can ask the
policies the question the real proposal will.

A policy you call yourself, in a unit test for example, has a context type with one more optional
field. Code that builds the context as `{ events, timeZone }` still compiles.

## State handlers hear why and who

The second argument of `onViewChange`, `onAnchorDateChange` and the other four state handlers had
`previous`, `controlled` and `slice`. It now also has:

| Field      | Contents                                                                                                                                                |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `reason`   | `"next-press"`, `"previous-press"`, `"today-press"`, `"input-change"`, `"keyboard-navigation"`, `"focus-change"`, `"resource-toggle"` or `"imperative"` |
| `source`   | `"mouse"`, `"touch"`, `"pen"`, `"keyboard"`, `"virtual"`, `"programmatic"` or `"agent"`                                                                 |
| `event`    | The DOM event, when one of the calendar's own controls caused the change                                                                                |
| `cancel()` | Keeps the value as it was                                                                                                                               |
| `canceled` | Whether a handler cancelled                                                                                                                             |

`"keyboard"` is a person's keys, on a toolbar button and in a view: arrow-key navigation, moving
focus and expanding a resource report it. `"programmatic"` is a call from your own code, and
`"agent"` anything an [agent's step](/docs/agents/changes#two-kinds-of-change) causes.

Handlers still run when they did: before a controlled value changes, since your handler is what
changes it, and after an uncontrolled one. `cancel()` puts an uncontrolled value back.
[State](/docs/concepts/state#what-a-handler-hears) has an example.

This breaks one thing: a test or a wrapper that builds a `CalendarStateChangeDetail` object by
hand. Add the new fields, or let the calendar make the detail by calling an action.

## Actions take options

`setView`, `setAnchorDate`, `setTimeZone`, `setSelection`, `setFocus`, `setExpandedResourceIds`,
`navigateNext`, `navigatePrevious` and `navigateToday` take an options object last:
`{ event?, reason?, source? }`. It says why the app made the call, and a state handler reads it
back.

Calls without it are unchanged. One pattern stops compiling: a navigation action passed directly
as an event handler. TypeScript reports that the click event "has no properties in common with
type `CalendarCommandOptions`". Wrap the call, and pass the event if a handler should hear it:

<include meta='title="next-button.tsx"'>../examples/migrating-next-button.tsx</include>

`Calendar.NextTrigger`, `Calendar.PreviousTrigger` and `Calendar.TodayTrigger` already do this.

## The parts have `data-slot`

`Calendar.Frame` and the toolbar parts are ui-sdk slots now, and each renders a `data-slot`
attribute beside its `data-calendar-part`:

| Part              | `data-slot`                 |
| ----------------- | --------------------------- |
| `Frame`           | `calendar`                  |
| `Toolbar`         | `calendar-toolbar`          |
| `Title`           | `calendar-title`            |
| `Viewport`        | `calendar-viewport`         |
| `PreviousTrigger` | `calendar-previous-trigger` |
| `TodayTrigger`    | `calendar-today-trigger`    |
| `NextTrigger`     | `calendar-next-trigger`     |
| `ViewSwitcher`    | `calendar-view-switcher`    |

They matter when your app already targets one of those names, and `calendar` is the likely one:
shadcn's date picker renders `data-slot="calendar"` on its root. A rule such as `[data-slot="calendar"] { … }`, or a test's
`querySelector('[data-slot="calendar"]')`, written for the date picker now matches the scheduler's
frame too. Scope such a selector to the date picker, or select the scheduler by
`data-calendar-part="frame"`.

## Add the registry's items again

In 1.x the registry's Tailwind items used shadcn's `button`, `badge`, `tooltip`, `select`,
`popover` and `dialog` from your app's `components/ui`, and Base UI's toast, so a change you made
there changed the calendar too, and your app needed a Base UI style. In 2.0 they use
`calendar-ui`, the calendar's own controls, built on ui-sdk, and no longer need Base UI. The controls no longer follow your
app's `components/ui`: they look the same in every app, and you restyle them in their own files.
They are a default and the files are yours, so you can still put your own components in their
place. [Customization](/docs/customization) lists every way to change the calendar's UI.

1. Add the items you use again, or all of them:

   ```bash
   npx shadcn@latest add https://time.molten.sh/r/calendar-full.json
   ```

   This now installs `calendar-ui` too: `button.tsx`, `badge.tsx`, `tooltip.tsx`, `select.tsx`,
   `popover.tsx`, `dialog.tsx` and `toast.tsx` in `components/calendar/ui/`, with the classes each
   one uses in a `*.styles.ts` file beside it.
   It adds `@ui-sdk/core` and `@ui-sdk/react` if your app doesn't have them yet. `shadcn add` asks
   before it replaces a file you changed; redo your changes on the new files.

2. ui-sdk adds a little CSS to the page in a layer named `ui-sdk`. Name that layer before Tailwind
   in your global CSS, so Tailwind's utilities win over it:

   ```css title="globals.css"
   @layer ui-sdk;
   @import "tailwindcss";
   ```

   The calendar's popups, from the view select's list and the tooltips to the popovers, the
   recurrence dialog and the undo toast, open in the browser's top layer, through the Popover API,
   so the registry's items now need Chrome and Edge 114, Safari 17 or Firefox 125. In
   an older browser they render at the end of the page, and a server-rendered page doesn't
   hydrate them cleanly.

3. If you restyled the calendar's buttons, badges, tooltips, popovers, dialogs or the view
   switcher through `components/ui`, make those changes in `components/calendar/ui/` instead. To
   keep using your own components there, make those files render them, as
   [Use your own controls](/docs/theming#use-your-own-controls) shows.

4. The items no longer install shadcn's components or `@base-ui/react`, and any shadcn style
   works. Keep the ones your app uses itself; the calendar doesn't need them. An app without
   shadcn's tokens can add `base-tokens`, as [UI source](/docs/installation#ui-source-optional)
   shows.

An [agent bridge](/docs/agents/connect) now lists the toolbar's buttons and the view select
beside the calendar, as `button` and `select` entries, and your `allow` hears the steps an agent
takes on them. The calendar's tooltips no longer need a `TooltipProvider`, and they don't follow
its `delay`: the toolbar's open after 400 ms, which `tooltipDefaults` in
`components/calendar/ui/tooltip.styles.ts` sets. The `stylex-` items don't change.

If you edited the views, a few of their own props changed with the move:

- `renderUnavailable` is a function of the band's props and its state, `(props, state) =>
element`. An element alone no longer works: wrap it in a function that spreads `props` on it.
- `AnnotationMark`'s `render` takes an element, and the mark's props merge into it. A function no
  longer works.
- The history toast's `recordedAnnouncement(step, title)` message is now
  `recordedHint(step)`. It returns only the part after the toast's title, such as "To undo it,
  press F6 and choose Undo.", since the title is read first. A screen reader now reads every toast
  as it shows, after the announcement of the gesture that caused it.
- A popover trigger has `aria-expanded` while its popover is open, in place of Base UI's
  `data-popup-open`. Style it with `aria-expanded:`.
- The time grid's event tooltips share one tooltip per view. A composition that renders
  `TimeGridEvent` outside the registry's views wraps them in `TimeGridEventTooltip` to do the
  same; without it, each event brings its own.

## Name the calendar

`Root` takes three new props:

| Prop                    | Effect                                                                                                                                |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `label`                 | Names the calendar. `Calendar.Frame` takes it as its `aria-label`, and an agent finds the calendar by it                              |
| `allowAgentDelete`      | Gives an agent the `deleteEvent` action. Off by default: the calendar has no such action then, and refuses any delete an agent causes |
| `formatAgentEventLabel` | Names each visible event in the list an agent reads. By default the title and ISO times                                               |

Without `label`, the frame is labelled by the title, as in 1.x, so nothing changes for a screen
reader until you set it. With `label`, the frame's name is the label and the title is no longer
part of it. `useCalendarMeta()` has the label as `meta.label`.

## Make it agent-ready

Upgrading exposes nothing. An agent reaches a calendar only after your app creates a bridge.
When you want that:

1. Give `Root` a `label`.
2. Render `Calendar.Frame` inside `Root`. A calendar without a frame works for people and isn't
   listed for agents.
3. Read `detail.fields` in `onEventChange`, so a title an agent sends is saved. See
   [Save what the agent sent](/docs/agents/connect#save-what-the-agent-sent).
4. Create the bridge with an `allow`, as [Connect an agent](/docs/agents/connect) shows.

A calendar without `onEventChange` gives an agent the reading and navigation actions and no
event action, as it gives a person no editing.

## New packages

| Package                           | What it is                                             | Install it when                   |
| --------------------------------- | ------------------------------------------------------ | --------------------------------- |
| `@moltenship/calendar-primitives` | The framework-free runtime, store and ui-sdk primitive | You write a framework integration |
| `@moltenship/calendar-solid`      | The Solid integration, a preview                       | Your app is on SolidJS 2          |

`createCalendarStore`, `resolveViewOptions` and the state types moved from
`@moltenship/calendar-react` into the primitives. Both `@moltenship/calendar` and
`@moltenship/calendar-react` re-export them, so imports from either still work and a store you
created keeps its contract. See [Primitives](/docs/api/primitives).

## The pointer hook moved

`@moltenship/calendar-dnd` imports no framework in 2.0, and `@moltenship/calendar-solid` binds it too. Its
one React hook, `useCalendarPointer`, is in `@moltenship/calendar-react` now, with the same
options and return value. `@moltenship/calendar` exports it as before, so an import from the
facade doesn't change. An import from the pointer package does:

```ts title="my-week-view.tsx"
// 1.x
import { useCalendarPointer } from "@moltenship/calendar-dnd";
// 2.0
import { useCalendarPointer } from "@moltenship/calendar-react";
```

Everything else in `@moltenship/calendar-dnd` stays where it was: `attachCalendarPointer`,
`startCalendarDrop`, `monitorCalendarDrags` and the attribute helpers. It no longer has React as a
peer dependency.

### With React but without calendar-react

An app that used `@moltenship/calendar-dnd` in React without `@moltenship/calendar-react` has two
ways on:

- **Add `@moltenship/calendar-react`** and its peers, `@ui-sdk/core` and `@ui-sdk/react`, then
  import the hook from it as above.
- **Keep the hook in the app.** It's a few lines around `attachCalendarPointer`:

```tsx title="use-calendar-pointer.ts"
import type { EventId, ResourceId } from "@moltenship/calendar-core";
import { attachCalendarPointer, type CalendarPointerOptions } from "@moltenship/calendar-dnd";
import { useCallback, useInsertionEffect, useRef, type RefCallback } from "react";

export function useCalendarPointer<
  TEvent,
  TEventId extends EventId,
  TResourceId extends ResourceId,
>(options: CalendarPointerOptions<TEvent, TEventId, TResourceId>): RefCallback<HTMLElement> {
  const latest = useRef(options);
  useInsertionEffect(() => {
    latest.current = options;
  });
  const disabled = options.disabled === true;
  // Options are read as a gesture goes; only `disabled` attaches the listeners again.
  return useCallback(
    (element: HTMLElement | null) =>
      element === null ? undefined : attachCalendarPointer(element, () => latest.current),
    [disabled],
  );
}
```

Either way, keep every `@moltenship/calendar*` package on one version. `@moltenship/calendar-react`
depends on `@moltenship/calendar-dnd` at its own exact version, and the pointer package keeps its
drag registry in the module: two copies of it don't hear each other's drags, so a drop from one
never reaches a view bound through the other.

## Tests

- **Scripted clicks.** A click a test dispatches reads `source: "programmatic"` in a state
  handler. Only a real pointer reads `"mouse"`.
- **The frame's name.** A test that finds the frame by its accessible name finds the `label` once
  you set one.
- **The registry's controls in jsdom.** They're ui-sdk's, which read paint timing, measure
  toasts and wait for transitions, none of which jsdom has, and jsdom hides every popup. Add the
  stubs [Testing](/docs/testing#set-up-vitest) lists to your test setup file.
- **Agent changes.** [Testing](/docs/testing#changes-an-agent-makes) shows how to run an agent's
  step in a test.
