---
title: Interactions
description: Save moved, resized, created, and deleted events, show them while they save, and decide which changes to allow.
---

Time never edits your events itself. When someone moves, resizes, creates, or deletes an event, the
calendar **proposes a change**. Your `onEventChange` handler saves it and updates your events. While
it saves, the calendar shows the change as **pending**; if saving fails, the event goes back to where
it was.

This page uses the `Calendar` and `Meeting` from the [Quick start](/docs/quick-start).

## Saving changes

Pass `onEventChange` to `Root`. Without it, the calendar is read-only.

<include meta='title="editable-calendar.tsx"'>../examples/editing.tsx#root</include>

The handler receives a change object:

| Field      | Contents                                                                                             |
| ---------- | ---------------------------------------------------------------------------------------------------- |
| `cause`    | `"move"`, `"resize-start"`, `"resize-end"`, `"create"`, `"delete"`, or `"update"`                    |
| `eventId`  | The event's ID, or `null` for `"create"`                                                             |
| `event`    | Your record, or `null` for `"create"`                                                                |
| `original` | Where the event was, as the user saw it, or `null` for `"create"`                                    |
| `proposed` | Where it should go: a range with `kind`, `start`, `end`, and `resourceIds`, or `null` for `"delete"` |
| `id`       | Identifies the change within this calendar, such as `change-3`. It isn't an event ID                 |

`applyChange` turns a change into new state. A created event needs an ID of your own, usually from
your server; this example makes one up. Records you don't touch stay the same objects, which keeps
re-rendering cheap:

## Pending changes

How long a change stays pending depends on your handler:

- **A handler that returns nothing** (or doesn't `await`) commits the change right away. Update your
  events in the same handler.
- **A handler that returns a promise** keeps the change pending until the promise settles. The event
  shows in its new place in the meantime.
  - If the promise resolves, the change stays visible until your `events` include it, so the event
    never jumps back.
  - If it rejects or the handler throws, the change is undone.

<include meta='title="editable-calendar.tsx"'>../examples/editing.tsx#save</include>

Pending events have `isPending: true` in projections, in `meta.eventSnapshot`, and in
`Calendar.Event`. The built-in views render them at 60% opacity: the week and day views set
`data-pending` on them, and the month and agenda views set `aria-busy`. Target those attributes to
style pending events your own way.

If the same event changes again before the first change finishes saving, the newer change wins.

## Policies

Policies decide which changes are allowed. Each one looks at a change and accepts it, adjusts it,
or rejects it. They run in order, and each sees the change as adjusted by the ones before it. Pass
them to `Root` as `policies`, as in the example above.

| Policy                                   | What it does                                                                                                               |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `snapPolicy({ minutes: 15 })`            | Rounds timed changes to a grid in the calendar's time zone                                                                 |
| `minimumDurationPolicy({ minutes: 15 })` | Lengthens timed events that would be shorter than the minimum                                                              |
| `boundsPolicy({ start, end })`           | Rejects changes that end up outside the given instants                                                                     |
| `readOnlyPolicy()`                       | Rejects changes to events your adapter marks with `isReadOnly`. `Root` always runs it first, so you don't need to pass it. |

A policy is a function, so you can write your own. This one keeps meetings out of the all-day row.
Policies can also be `async`, for example to check availability on your server.

## Changing events from your own UI

Buttons, forms, and dialogs can propose changes too, with `proposeEventChange` from
`useCalendarActions()` (or the `actions` prop inside a view). The change goes through the same
policies, pending state, and handler as a drag. The returned promise tells you how it ended; it
never rejects.

<include meta='title="push-back-button.tsx"'>../examples/editing.tsx#propose</include>

A rejected result has a `reason`:

| `reason`            | Meaning                                                           |
| ------------------- | ----------------------------------------------------------------- |
| `read-only`         | The event is read-only, or `Root` has no `onEventChange`          |
| a policy's reason   | A policy rejected it, such as `out-of-bounds`                     |
| `superseded`        | A newer change for the same event replaced it                     |
| `handler-error`     | Your handler threw or its promise rejected; `error` has the cause |
| `policy-error`      | A policy threw                                                    |
| `invalid-placement` | The proposed range is empty or reversed                           |
| `unknown-event`     | No event has that ID                                              |

To create an event, propose `{ cause: "create", proposed: { kind, start, end } }`. To delete one,
propose `{ cause: "delete", eventId }`.

## Drag, resize, and create

`@moltenship/calendar-dnd` turns pointer gestures into proposals: drag an event to move it, drag its
top or bottom edge to resize it, and drag across empty time to create one. It works with mouse,
pen, and touch (on touch screens, press and hold for a moment first).

<Callout title="Coming to the built-in views">
  The built-in views already render the markup the pointer layer needs. Connecting it to them is in
  progress; until then, you can add it to your own views as shown below.
</Callout>

In a view's Renderer, call `useCalendarPointer` with the props the Renderer receives, and put the
returned ref on the element that contains the days:

```tsx title="my-week-view.tsx"
import { defineCalendarView, timeGridStrategy } from "@moltenship/calendar";
import { useCalendarPointer } from "@moltenship/calendar-dnd";

export const myWeekView = defineCalendarView({
  name: "week",
  strategy: timeGridStrategy({ kind: "week" }),
  Renderer: function MyWeek({ actions, environment, events, projection }) {
    const ref = useCalendarPointer({
      columns: projection.days.map((day) => day.column),
      events,
      onPropose: actions.proposeEventChange,
      timeZone: environment.timeZone,
    });

    return <div ref={ref}>{/* Day columns with data-date, events with data-event-id */}</div>;
  },
});
```

Pass `columns` only in time-grid views; a month grid finds days by their `data-date`. The hook reads
these attributes from your markup:

| Element                                        | Attribute                        |
| ---------------------------------------------- | -------------------------------- |
| A day column in a time grid, covering 24 hours | `data-date="2026-10-08"`         |
| An all-day cell                                | `data-date="…" data-all-day`     |
| A day cell in a month grid                     | `data-date="…"`                  |
| An event (render it as a `<button>`)           | `data-event-id`                  |
| A resize handle inside an event                | `data-resize="start"` or `"end"` |

Each finished drag proposes exactly one change. A movement under 4px stays a click, and Escape
cancels a drag. Times snap to 15 minutes by default (set `snap` to change it), and the view scrolls
when you drag near its edges. Dragging never re-renders your view: the preview is drawn separately
and can be styled through `[data-calendar-ghost]`.
