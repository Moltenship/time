The packages don't ship any CSS. The styled parts in the registry read their colors and sizes from
CSS variables defined in `calendar-theme.css`. The `calendar-theme` item, which every view brings,
adds its tokens and rules to your global CSS, as described in
[UI source](/docs/installation#ui-source-optional). Override the variables in your own CSS to
restyle the calendar, as [Changing tokens](#changing-tokens) shows: each `shadcn add` writes the
theme's own block again. To try changes live and copy the CSS, use the
[Theme builder](/docs/theme-builder).

This page covers the Tailwind baseline. The `stylex-*` items keep the same token names, as StyleX
variables you override with `stylex.createTheme`; see [StyleX](/docs/stylex#change-the-tokens).

## Tokens

`calendar-theme.css` defines the standard shadcn/ui tokens (`--background`, `--primary`,
`--border`, and so on) plus these calendar tokens. `shadcn add` adds only the calendar tokens, since
your app has its own shadcn theme:

| Variable                      | Used for                                              | Tailwind class                    |
| ----------------------------- | ----------------------------------------------------- | --------------------------------- |
| `--calendar-surface`          | Behind sticky headers, between events                 | `bg-calendar-surface`             |
| `--calendar-grid`             | Lines between days and hours                          | `border-calendar-grid`            |
| `--calendar-axis`             | Hour and weekday labels                               | `text-calendar-axis`              |
| `--calendar-today`            | Today's date marker                                   | `bg-calendar-today`               |
| `--calendar-today-foreground` | Text on today's marker                                | `text-calendar-today-foreground`  |
| `--calendar-now`              | The current-time line                                 | `bg-calendar-now`                 |
| `--calendar-selection`        | Selected days and time ranges                         | `bg-calendar-selection`           |
| `--calendar-weekend`          | Weekend background                                    | `bg-calendar-weekend`             |
| `--calendar-unavailable`      | Closed time in time grids and timelines               | `bg-calendar-unavailable`         |
| `--calendar-closed`           | Closed days in the month and year views               | `bg-calendar-closed`              |
| `--calendar-busy`             | A resource status's busy dot                          | `bg-calendar-busy`                |
| `--calendar-free`             | A resource status's free dot                          | `bg-calendar-free`                |
| `--calendar-invalid`          | A preview the policies would reject                   | `outline-calendar-invalid`        |
| `--calendar-warning`          | A preview the policies would flag                     | `outline-calendar-warning`        |
| `--calendar-event`            | Event background                                      | `bg-calendar-event`               |
| `--calendar-event-foreground` | Event text                                            | `text-calendar-event-foreground`  |
| `--calendar-event-border`     | Event accent edge                                     | `border-calendar-event-border`    |
| `--calendar-hour-height`      | Height of one hour in time grids (`3rem`)             | `h-(--calendar-hour-height)`      |
| `--calendar-event-padding-x`  | Padding at the sides of time-grid events (`0.375rem`) | `px-(--calendar-event-padding-x)` |
| `--calendar-event-padding-y`  | Padding above and below time-grid events (`0.25rem`)  | `py-(--calendar-event-padding-y)` |

The color tokens work with any Tailwind color utility, so `text-calendar-today` and
`ring-calendar-now` work too. Most calendar tokens derive from the shadcn tokens: `--calendar-grid`
is your `--border`, and the default event colors mix your `--primary` into `--background`.

The event padding tokens set how roomy events are in the week, day and resource columns views,
along with `--calendar-hour-height`. The views fall back to the default padding where they read
them, so a copy of `calendar-theme.css` from before these tokens keeps working.

## Changing tokens

Every token is declared inside `@layer base`, so a plain rule in your own CSS wins without
`!important`. Set the light values on `:root` and the dark values on `.dark`:

```css title="globals.css"
:root {
  --calendar-today: oklch(0.55 0.17 150);
  --calendar-hour-height: 4rem;
}

.dark {
  --calendar-today: oklch(0.72 0.15 150);
}
```

If your app already defines the shadcn tokens, the calendar follows them automatically.

`--calendar-surface` is unset by default and falls back to `--background`. Set it on the
calendar's container when that container has its own background, such as a card, so sticky
headers and gutters match it:

```tsx
<main className="bg-card [--calendar-surface:var(--card)]">
```

## Dark mode

The theme switches when an ancestor of the calendar has the `dark` class, which is how shadcn/ui
and `next-themes` work. shadcn apps already define the matching Tailwind `dark` variant. If yours
doesn't, add `@custom-variant dark (&:is(.dark *));` below the imports in your global CSS.

## Event colors

The theme has a palette of nine event colors: `blue`, `green`, `red`, `orange`, `yellow`,
`purple`, `pink`, `teal`, and `gray`. Put one in a `data-color` attribute and that element's three
event tokens switch to the color, in both light and dark mode:

```html
<div data-color="green" class="bg-calendar-event text-calendar-event-foreground">Standup</div>
```

`EventChip`, the event button in `registry/calendar`, sets `data-color` from its `color` prop. The
names are exported from `event-colors.ts` as `calendarEventColors`, with the type
`CalendarEventColor`.

### Choosing a color per event

Every built-in view takes an optional `getEventColor` option: a function from your event record to
a color name. Pass it when you create the view, as the [Quick start](/docs/quick-start) does, or
per calendar with the `viewOptions` prop on `Root`:

```tsx
const getEventColor = (meeting: Meeting) => (meeting.title === "Standup" ? "green" : "blue");

// On Root:
viewOptions={{ month: { getEventColor }, agenda: { getEventColor } }}
```

Define the function outside your component, so it keeps its identity between renders. See
[Performance](/docs/guides/performance#keep-functions-in-options-stable). Without `getEventColor`,
events use the theme's default event tokens.

To support it in your own view, add it to the view's options and pass the result to `EventChip`:

### Adding a color

Each palette entry only sets a hue and a chroma; the `[data-color]` rule turns them into the three
event tokens for light and dark mode. To add a color, add its name to `calendarEventColors` in
`event-colors.ts` and give it a hue and chroma in your CSS:

```css title="globals.css"
[data-color="brand"] {
  --calendar-event-hue: 285;
  --calendar-event-chroma: 0.2;
}
```

## Use your own controls

The kit's files are your app's code once you add them: a default to edit or replace.

The Tailwind views take their buttons, badges, tooltips and the view select from the files
`calendar-ui` adds to `components/calendar/ui/`. They don't import ui-sdk themselves, and they
don't reach into a control's parts or attributes. To use a control of your own, replace the body
of its file: keep the file's name, the names it exports and the props below, and render your
component. The views stay as they are.

With shadcn's button, from a Base UI style, the button file is a few lines:

```tsx title="components/calendar/ui/button.tsx"
import type { ComponentProps } from "react";

import { Button as AppButton, buttonVariants } from "@/components/ui/button";

export type ButtonProps = ComponentProps<typeof AppButton>;

export function Button(props: ButtonProps) {
  return <AppButton {...props} />;
}

export { buttonVariants };
```

Pass on every other prop, `aria-*` and `data-*` included, to the element your control renders,
around its children. The views set them, and their CSS and tests read some of them. What the views
import from each file, and what they pass:

| File          | The views import                                                                       | What the views pass                                                                                                                                                                                                                                                            |
| ------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `button.tsx`  | `Button`                                                                               | `variant` (`outline`, `ghost`), `size` (`default`, `lg`, `icon`, `icon-sm`, `icon-xs`), `className`, `onClick`, `disabled`, `tabIndex`, `ref`, `aria-*`, `data-scope`, and `render`                                                                                            |
| `badge.tsx`   | `Badge`                                                                                | `variant="outline"`, `className`, `title`, and `data-slot="resource-status"` with `data-state`, which colours the status dot inside it                                                                                                                                         |
| `tooltip.tsx` | `Tooltip`, `TooltipTrigger`, `TooltipContent`                                          | `Tooltip`: `delay`. `TooltipTrigger`: `render`, the button it shows on. `TooltipContent`: the text, and `side`, `align`, `sideOffset` and `className`                                                                                                                          |
| `select.tsx`  | `Select`, `SelectTrigger`, `SelectValue`, `SelectContent`, `SelectGroup`, `SelectItem` | `Select`: `items` (`{ label, value }`), `value` and `onValueChange`, which gets the new value. `SelectTrigger`: `aria-label` and `className`. `SelectContent`: `align` and `alignItemWithTrigger`. `SelectItem`: `value`, `label`, and the label with its shortcut as children |

The kit's files also export `buttonVariants`, `badgeVariants`, `SelectGroupLabel` and
`SelectSeparator` for your own code. Keep them, or remove what you don't use.

`render` is an element to render in place of the `<button>`. The toolbar passes the calendar's
`TodayTrigger`, `PreviousTrigger` and `NextTrigger` this way: the trigger keeps its own props and
runs the command, and your button adds its look and passes on `disabled`. If your button takes
`asChild` instead, as a Radix style's does, render the `render` element as its child with
`asChild`. Typing on the view select matches each item's `label`, so pass it on to your select's
items.

A control that isn't built on ui-sdk gives up two things:

- **What an agent sees.** An [agent bridge](/docs/agents/connect) lists ui-sdk's components. It
  reads your control only as far as your component tells it, and a stock shadcn control tells it
  nothing. The calendar stays on the bridge, so an agent can still change the view with its
  `setView` action.
- **The same control in React and Solid.** The kit's controls behave alike in both frameworks
  because both build on ui-sdk's. Yours behaves as your component does, so a Solid app needs its
  own version of it.
