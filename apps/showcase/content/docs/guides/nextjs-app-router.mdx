title: Next.js App Router example
description: A calendar whose view and date live in the URL, loaded by a Server Component and saved through Server Actions.
---

[Next.js and server rendering](/docs/guides/nextjs) covers the basics: Client Components, strings
instead of Temporal values, and `now` and the time zone from the server. This page walks through a
complete App Router route built on them. [Open the example](/examples/nextjs), then read its source
here. To load events in the browser from an API instead, see
[Load events with TanStack Query](/docs/guides/tanstack-query).

- **The URL holds the view and the date**, as in `/examples/nextjs?view=week&date=2026-10-12`.
  Previous, next, Today and the view switcher change it, and Back and Forward work.
- **A Server Component fetches the meetings** for the range the URL shows.
- **Server Actions save** created, moved and resized meetings. The calendar proposes each change, the
  server decides, and the page renders again with the result.
- **The time zone comes from a cookie**, and the first render's clock from the server.

The route has eight files:

| File                | Kind             | What it does                                              |
| ------------------- | ---------------- | --------------------------------------------------------- |
| `layout.tsx`        | Server Component | The heading and the frame, which stay put as pages change |
| `page.tsx`          | Server Component | Reads the URL and the cookies, and fetches the meetings   |
| `loading.tsx`       | Server Component | The first load's skeleton                                 |
| `location.ts`       | Shared           | The URL's view and date, and the dates they show          |
| `meetings.ts`       | Server only      | An in-memory store that stands in for your database       |
| `actions.ts`        | Server Actions   | Save meetings and the time zone                           |
| `calendar.ts`       | Client           | The calendar, its views and its policies                  |
| `team-calendar.tsx` | Client Component | The calendar's state, wired to the URL and the actions    |

## The page

The page is a Server Component. It reads the URL, the visitor and the clock, and fetches the
meetings for the range the calendar will show:

<include meta='title="page.tsx"'>../../../app/(home)/examples/nextjs/page.tsx#page</include>

- **It renders on every request.** Reading `searchParams` and cookies makes the page dynamic.
- **`now` is read once**, here, and passed down as a string, so the server and the browser render
  the same today. Once the page has hydrated, the calendar follows the browser's clock instead, so
  the now line keeps moving between server renders.
- **Meetings arrive as strings.** `meetings.ts` sends them as `MeetingJson`, with ISO 8601 times:

<include meta='title="meetings.ts"'>../../../app/(home)/examples/nextjs/meetings.ts#types</include>

The server works out the dates with the functions the views use, so it fetches exactly what they
show. The example's tests check that the two agree for every view:

<include meta='title="location.ts"'>../../../app/(home)/examples/nextjs/location.ts#range</include>

`visibleRange` turns the dates into instants in the visitor's time zone, as `Root` does for
`onVisibleRangeChange`. A week in Tokyo starts nine hours before a week in UTC.

`view` and `anchorDate` are controlled, so the URL decides what the calendar shows. `timeZone` is

`now` is the server's for that first render and the calendar's own clock after it.

## Navigation

When someone moves to another week or view, the calendar calls `onAnchorDateChange` or
`onViewChange`. The component pushes a new URL instead of keeping the change in state:

<include meta='title="team-calendar.tsx"'>
  ../../../app/(home)/examples/nextjs/team-calendar.tsx#navigation
</include>

- **The grid moves on the click.** `router.push` runs inside a transition, and `useOptimistic` shows
  the new view and date at once. Their meetings arrive with the server's render. Until then the grid
  shows the meetings it already has that fall in the new range: all of them when zooming from a
  month into a week, none when stepping to the next week.
- **The page says it's loading.** The transition's `loading` flag sets `aria-busy` on the viewport
  and shows a thin bar under the toolbar. The grid itself never blanks.
- **One click, one URL.** Opening a day from the month view changes the view and the date. The
  changes queue for one microtask, so they land in a single URL and a single history entry.
- **Back and Forward** restore that URL's render from the Next.js router's cache, or fetch it again
  when it isn't cached, as after a save or a zone change. The controlled props follow.

The calendar stays mounted through all of this. Next.js keeps the page on screen while it fetches
the next render, and the props change in place, so the scroll position and the focus survive.
`loading.tsx` only shows when the route first loads, before there's a page to keep:

## Saving

The calendar proposes; the app commits. Every move, resize and create runs through the calendar's
policies first, then reaches `onEventChange`, which calls a Server Action:

<include meta='title="actions.ts"'>../../../app/(home)/examples/nextjs/actions.ts#actions</include>

- **Check every argument.** A Server Action is a public endpoint, and anyone can call it with
  anything. The calendar's snap and minimum duration don't protect the server.
- **The server has the last word.** This one refuses meetings that start in the past, a rule the
  calendar doesn't know.
- **`refresh()` re-renders the page** in the same response as the action's result, so the saved
  meeting arrives without another request. If your reads are cached with `"use cache"`, call
  `updateTag` instead.
- **Saves run one at a time.** Next.js sends a page's Server Actions in order, so two quick moves of
  one meeting are saved in the order they were made.

On the client, `save` turns the action's result into the promise the calendar waits for:

<include meta='title="team-calendar.tsx"'>
  ../../../app/(home)/examples/nextjs/team-calendar.tsx#save
</include>

- **Moves and resizes** stay where they were dropped while the promise is pending. The calendar
  shows them as saving, then keeps them in place until the page's next render has the saved times.
- **A refusal** rejects the promise, and the calendar moves the meeting back. The reason shows under
  the calendar.
- **New meetings** have no ID until the server gives them one, so the calendar can't show them as
  pending. `useOptimistic` adds them to the meetings on screen until the page renders again with the
  saved one. They're marked `pending`, and the adapter's `isReadOnly` keeps them still until then.

## The time zone

The page renders in the zone from the `time-zone` cookie. On a first visit there's no cookie, so the
server renders in UTC, and the browser sends its own zone once it has hydrated:

<include meta='title="team-calendar.tsx"'>
  ../../../app/(home)/examples/nextjs/team-calendar.tsx#time-zone
</include>

`useOptimistic` switches the calendar to the new zone at once. Setting a cookie in a Server Action
re-renders the page in the same response, so the meetings for the new zone's range arrive with the
action's result. Every later request renders in the right zone from the start, and hydration
matches. The picker under the calendar calls the same action.

Switching zones keeps each meeting at its instant, so a 09:30 standup in Tokyo shows in the small
hours in Berlin. A first visit has no zone to keep, so its sample meetings simply follow the browser's.

## Temporal in the browser

The server runs on Node.js 26, which has `Temporal`. The calendar also renders while the page
hydrates, so `Temporal` has to exist in the browser before then. `team-calendar.tsx` imports
`temporal-polyfill/global` before anything else. The polyfill installs itself only in browsers
without `Temporal`, but as a static import every browser downloads it. The dynamic import that
[Installation](/docs/installation#temporal) shows saves that, but only suits a calendar that renders
after hydration.

## Make it yours

- **Replace `meetings.ts`** with your database. Its functions take the visitor and a range, as
  queries would.
- **Use your auth** in place of the session cookie, and check in every action that the visitor owns
  the meeting they're changing.
- **Refuse stale writes.** Give meetings a revision, send it with each change, and refuse a change
  made to an older one. The adapter's `getRevision` tells the calendar about them.
  [Sync with Google Calendar](/docs/guides/google-calendar-sync) does the same with etags.
- **Cache the reads** with `"use cache"` and `cacheTag`, and call `updateTag` from the actions.
